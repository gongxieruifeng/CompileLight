结合 SKILLFLOW 的核心精髓（DAEF 骨架、补丁修复、反代码膨胀），你的 Dify + LangGraph 架构可以在以下三个维度进行深度重构与借鉴：

### 一、 经验切分：从“端到端流水账”升级为“DAEF 骨架 + 原子 FSM”

你目前的 JSON 模板是把“查知识库 ➔ 创工单 ➔ 发邮件”写死在一个流程里。为了解决 60% 匹配的问题，我们需要引入 SKILLFLOW 中的 **DAEF（领域无关执行流）** 思想。

**解决思路：**
不要把具体的工具调用链作为最小单位，而是将经验切分为两个层级：

1. **宏观骨架（Macro Skeletons / DAEF）：** 沉淀高度抽象的逻辑拓扑。例如 `[信息检索] ➔ [数据规范化] ➔ [系统写入] ➔ [通知分发]`。这个骨架不绑定具体工具，只定义数据流向。
2. **原子 FSM（Micro Sub-graphs）：** 沉淀具体的、高内聚的微型工作流。比如“查询 Jira 并提取核心字段”是一个原子 FSM，“发送并校验内部邮件”是另一个原子 FSM。

**当遇到 60/40 场景时：**
Agent 不再是复用一整个死板的 JSON，而是**复用那个 60% 匹配的“原子 FSM”**。剩下的 40%，由 Agent 的系统二（慢思考）动态调用其他已有的 FSM，或者临时推理新的步骤，最后拼装在宏观骨架上。

### 二、 动态编排：在 LangGraph 中实现“乐高式”的图拼接

为了让 60% 和 40% 能够丝滑融合，LangGraph 在你的系统中不能仅仅是一个“死脚本执行器”，它需要具备**子图动态拼接（Dynamic Sub-graph Routing）** 的能力。

* **原来的逻辑：** 拿到经验 JSON ➔ 翻译成 LangGraph 节点 ➔ 顺序列车执行。
* **进化后的逻辑：**
* **60% 旧任务：** Agent 将这部分直接映射到 LangGraph 已经固化好的高频 `Sub-graph`（即那个已验证的经验节点），这部分执行是 **0 Token 消耗**的“肌肉记忆”。
* **40% 新任务：** Agent 使用极少量的 Token，规划出这 40% 的执行流。
* **运行态合成：** 将那 60% 的黑盒 FSM 与 40% 的新路径，动态编译成一张临时的 LangGraph 状态图去运行。如果这次拼接运行成功，这个“新拼图”的关联关系会被记录下来，成为下一次的候选经验。



### 三、 长期可用性：引入“批评者回路（Critic Loop）”与“补丁协议（Patch Protocol）”

如何保证系统长期可用、不变成“废铁库”？这是 SKILLFLOW 给我们最大的启示：**大模型之间真正的阶级鸿沟在于“修代码”的能力。**

在你的经验沉淀回路中，必须加上严酷的**经验治理与重构机制**：

* **拒绝无脑新增（Anti-Inflation）：** 当 Agent 成功解决了一个“60% 相似，40% 新颖”的任务后，不要直接生成一个全新的经验文档（这会导致经验库里存在大量 60% 重复的代码块）。
* **引入补丁协议（Incremental Patch）：**
后台必须跑一个定期的（比如每天凌晨）“治理 Agent”。它的工作类似于 SKILLFLOW 中的 Opus 4.6：对比新旧执行轨迹。如果发现新任务是对老经验的合理扩展，它应该生成一个 **JSON Patch (Upsert/Delete)**，将老经验重构为带有条件分支的更强大的 FSM，而不是新增一条记录。
* **红字报错与自修复（Self-Repair）：**
如果某个复用经验（比如那个 60% 的 FSM）因为底层 API 变更报错了，LangGraph 需要将详细的报错堆栈作为“环境硬约束反馈”抛给 Dify 的系统二。系统二必须具备 `Update_Experience_Template` 的工具权限，在完成当前任务后，顺手把经验库里的那个错误参数给“修”了。

### 四、 架构升级前后对比

| 核心维度 | 当前《Token Reduce Plan》设计 | 融合 SKILLFLOW 后的进阶设计 |
| --- | --- | --- |
| **经验存储形态** | 包含 100% 完整任务流的静态 JSON | **DAEF 宏观骨架** + **高度内聚的原子 FSM (子图)** |
| **部分匹配(60/40)策略** | 降级为 `REFERENCE`，放入 Prompt 让 LLM 重新规划，浪费大量 Token | **子图复用**：60% 走肌肉记忆（0 Token），40% 由 LLM 动态桥接或推理 |
| **经验进化方式** | 不断总结成功案例，**Append (追加)** 到向量库中 | **Patch (补丁重构)**：合并相似经验，修剪冗余节点，防止认知过载 |
| **纠错机制** | 依赖人工审核或失败后重新走系统二 | **闭环修复**：通过报错报告反推修补现存 FSM，保持外部记忆库健康 |

将长流程打碎成“宏观拓扑 + 原子节点”，并通过“补丁更新”取代“全量新增”，是让你的 Agent 具备真正的长期自我演进能力的关键。

对于把“经验”拆碎这件事情，你目前在 Dify 中定义的 Tool（工具）粒度，是偏向于非常底层的“原子 API 调用”（比如单纯的 GET 请求），还是已经包含了一定业务逻辑处理的“微服务”（比如查数据库并做去重合并）？

完全理解你的困惑。从“静态固化的长流程”跨越到“动态拼合的原子子图”，这确实是整个架构演进中最陡峭、也最吃工程功底的一步。

我们可以把传统的静态 JSON 方案理解为“录制了一整段宏指令”**，只要其中一步对不上，整段代码就全废了。而 DAEF 与原子 FSM 的方案，本质上是在打造一套**“动态乐高引擎”。

为了让你在底层实现上有清晰的抓手，我们把这个过程拆分为“如何切分（Build）”**和**“如何拼合（Assemble）”两个核心阶段来展开。

### 一、 最初 FSM 的切分与构建（沉淀阶段）

系统是如何知道一段长流程中，哪部分该被切成“原子 FSM”，哪部分属于“DAEF 骨架”的？这需要一个后台治理机制（Critic Agent / 离线跑批脚本）介入。

当你的通用 Agent（系统二）成功完成了一次高成本的完全推理任务后，会留下一串长长的执行轨迹（Trace）。这时候不要直接把整串轨迹存下来，而是按以下步骤处理：

* **输入输出边界探测：** 后台脚本分析这串轨迹，寻找“数据形态发生根本改变”的节点。例如，前面 3 步都在查询各类 API 组装上下文（获取信息），第 4 步开始将数据转化为特定格式（处理信息），最后两步调用邮件和 Jira 接口（执行输出）。
* **提取原子 FSM：** 脚本将上述高内聚的步骤（如“查询各类 API 组装上下文”）打包，剥离掉具体的业务参数，生成一个独立的 `Sub_Graph_Template`（JSON 格式）。这就形成了一个“肌肉记忆”模块，比如命名为 `FSM_Data_Gathering`。
* **抽象 DAEF 骨架：** 脚本同时提取出这次任务的宏观拓扑，例如生成一个骨架：`[FSM_Data_Gathering] ➔ [LLM_Decision] ➔ [FSM_System_Write]`。
* **入库注册：** 这些 FSM 模板和 DAEF 骨架被存入向量数据库。每个 FSM 都会带有明确的描述（Description）和所需的入参/出参接口定义。

### 二、 运行时的动态拼合细节（调用阶段）

这是最关键的环节：当新任务只有 60% 匹配时，LangGraph 是如何实现动态拼接的？

**核心思路：不要试图在运行时用代码去“凭空画一张新图”，而是设计一个“元解释器工作流（Meta-Router Graph）”。**

在你的 LangGraph 侧，部署的是一个通用循环图，它接受一个**执行蓝图（Blueprint）**，然后负责按蓝图调度。

**具体拼合流程如下：**

1. **意图解析与检索（极轻量 LLM 消耗）：**
用户输入新任务。Dify 中的 Agent 去检索经验库，发现没有 100% 匹配的长流程，但检索到了一个 60% 匹配的 `FSM_查询 Jira 核心字段`，以及一个可用的 DAEF 骨架。
2. **生成动态蓝图（Blueprint Generation）：**
Agent 的 System Prompt 会引导它基于检索到的 DAEF 骨架和原子 FSM，填补那缺失的 40%。它会输出一个结构化的执行数组（Blueprint）：
```json
[
  {"step": 1, "type": "fsm", "name": "FSM_查询Jira核心字段", "inputs": {"ticket_id": "xxx"}},
  {"step": 2, "type": "tool", "name": "临时推理_调用企业微信发消息", "inputs": {"msg": "{{step_1.output}}"}},
  {"step": 3, "type": "fsm", "name": "FSM_写入本地日志", "inputs": {"status": "success"}}
]

```


*在这份蓝图中，步骤 1 和 3 是那 60% 的历史经验，步骤 2 是那 40% 的新推理。*
3. **LangGraph 元解释器执行（动态组装）：**
Dify 将这份 Blueprint 发给 LangGraph。LangGraph 内部的逻辑非常固定：
* **读取 Step 1：** 发现是 `type: fsm`。LangGraph 的当前节点会动态加载（Load）对应的子图配置，像调用普通函数一样，确定性地执行这个 FSM，全程 **0 LLM Token 消耗**。执行完毕，结果放入全局上下文。
* **读取 Step 2：** 发现是 `type: tool`（那 40% 的未知部分）。此时触发普通的工具调用节点，执行企业微信发消息动作。
* **读取 Step 3：** 再次遇到 FSM，加载执行，直到蓝图跑完。

### 三、 新旧方案执行对比

| 环节 | 原静态 JSON 方案 (100% 匹配) | 动态原子 FSM 方案 (60/40 匹配) |
| --- | --- | --- |
| **匹配失败结果** | 直接回退到慢思考，从头开始规划，耗费大量 Token | 保留 60% 的确定性执行，仅对 40% 差异部分进行规划 |
| **LangGraph 职责** | 执行一条写死的单向流水线 | 作为元解释器，动态调度 FSM 子图与单点工具 |
| **经验库健康度** | 容易堆积大量重复的长流程（技能膨胀） | 沉淀高复用率的子图，像代码库的通用函数一样干净 |

这种“生成蓝图 ➔ 解释器按蓝图调度子图”的模式，完美避开了在运行时动态编译底层代码的风险，又实现了经验的灵活复用。

既然我们需要在后台从历史执行轨迹中提炼这些“原子 FSM”，你目前的系统中，对于 Agent 的执行日志（比如它调用了哪些工具、输入输出参数是什么），是否有进行结构化的落盘存储？

这是一个非常硬核且直指系统命脉的工程问题。把经验拆成“原子 FSM”和“DAEF 骨架”后，如果不解决**存储结构**和**高效精确匹配**的问题，整个系统就会变成一个检索缓慢、错误率极高的“垃圾堆”。

要实现你想要的“像人一样瞬间激活相关肌肉记忆”，我们需要一套“向量检索 + 结构化元数据 + 轻量级重排”的混合架构。以下是具体的落地方案。

### 一、 存储架构与数据结构

为了满足既能进行模糊的“语义匹配”，又能进行精确的“蓝图提取”，强烈建议采用 **双引擎存储** 或 **支持丰富元数据的向量数据库**（如 PostgreSQL + PGVector，或 Qdrant、Milvus）。

数据库中需要建立两个核心集合（Collections/Tables）：**原子 FSM 库** 和 **DAEF 骨架库**。

#### 1. 原子 FSM（子图）的数据结构

FSM 存的不能只是执行代码，必须像微服务 API 一样，拥有极度清晰的“自我声明”。

```json
{
  "fsm_id": "fsm_jira_extract_001",
  "name": "Jira工单核心信息提取器",
  "semantic_description": "通过工单号查询Jira系统，提取工单的状态、经办人、优先级和最新评论。适用于任何需要获取工单当前进展的场景。",
  "required_inputs": [
    {"name": "ticket_id", "type": "string", "description": "Jira工单号，例如 IT-1234"}
  ],
  "outputs": [
    {"name": "status", "type": "string"},
    {"name": "assignee", "type": "string"},
    {"name": "latest_comment", "type": "string"}
  ],
  "execution_graph": [
    // 这里存放实际供 LangGraph 元解释器加载的节点流定义
    {"step": 1, "tool": "jira_api_get", "params": {"id": "{{ticket_id}}"}},
    {"step": 2, "tool": "json_parser", "params": {"path": "$.fields..."}}
  ],
  "metadata": {
    "domain": "IT_Support",
    "success_rate": 0.98,
    "usage_count": 520,
    "last_updated": "2026-06-15"
  }
}

```

#### 2. DAEF 骨架的数据结构

骨架存储的是“高维度的解决问题套路”，它甚至可以不包含具体的工具，只包含抽象的意图流。

```json
{
  "daef_id": "daef_query_and_notify_01",
  "semantic_description": "查询某系统的状态，分析结果，并将结论通过通讯工具通知用户。",
  "abstract_steps": [
    "Information_Retrieval (信息获取)",
    "Data_Normalization (数据分析与标准化)",
    "Notification_Dispatch (通知分发)"
  ]
}

```

### 二、 经验检索与匹配机制（算法/机制）

当用户输入一个新任务时，Agent 如何精准捞出那 60% 匹配的 FSM？这绝对不能仅靠单调的向量检索（Dense Retrieval），因为向量检索容易丢失“Jira”、“工单号”这种精准的关键实体信息。

我们需要构建一条 **混合检索与动态重排（Hybrid Search & Reranking）** 链路：

#### 第 1 步：混合检索 (Hybrid Search) 召回候选集

当用户输入任务，例如：*“帮我查一下 IT-8899 这个工单现在是谁在处理，然后发企业微信告诉我。”*

* **向量检索 (Dense)：** 将用户的自然语言转化为向量，去匹配数据库中 FSM 的 `semantic_description`。这能召回所有与“查工单”、“发通知”语义相关的组件。
* **字面量检索 (Sparse / BM25)：** 提取用户输入中的关键词（如“企业微信”、“IT-8899”），去精确匹配 FSM 的 `name` 和 `metadata.domain`。
* **结果合并：** 将两种检索结果按权重合并，捞出 Top 10 个最相关的候选 FSM 和 DAEF 骨架。

#### 第 2 步：LLM 轻量级路由重排 (Reranking & Blueprint Generation)

拿着捞出来的 Top 10 候选集，Dify 的编排 Agent（也就是决策路由 LLM，可以是一个便宜但逻辑能力强的模型，如 GPT-4o-mini 或 Claude-3.5-Haiku）开始工作。

我们在这个节点的 System Prompt 会这样设计：

> **[系统提示词示例]**
> 你是一个系统蓝图规划师。用户任务是：“帮我查一下 IT-8899 这个工单现在是谁在处理，然后发企业微信告诉我。”
> 以下是系统可用的一些“肌肉记忆”（原子 FSM）：
> 1. [FSM: jira_extract_001] 功能：提取工单信息。入参：ticket_id。出参：status, assignee。
> 2. [FSM: email_sender_002] 功能：发邮件通知。
> 
> 
> 请分析：
> 能否直接复用上述 FSM 完成部分工作？如果可以，请输出一个包含 FSM 和必要原生工具调用的 JSON 蓝图。

**LLM 的思考与输出机制：**

1. **匹配 60%：** LLM 发现 `jira_extract_001` 完美匹配了前半部分需求。
2. **发现 40% 的差异：** LLM 发现库里只有发邮件的 FSM，没有“发企业微信”的 FSM。
3. **生成执行蓝图：** LLM 决定组合使用。它输出一个 JSON 蓝图给 LangGraph：
* Step 1: 调用子图 `fsm_jira_extract_001` (传入 IT-8899)
* Step 2: 动态调用基础工具 `wechat_api_send` (传入 Step 1 的 assignee 结果)



#### 第 3 步：元数据的降维打击 (防劣化机制)

在上述检索过程中，`metadata` 发挥着决定性作用。如果两个 FSM 语义极其相似，匹配机制会自动参考 `success_rate`（成功率）和 `usage_count`（被调用次数）。那些成功率低于 80% 或很久没人用的“劣质 FSM”，会在检索阶段被降权，甚至直接被后台的 Critic Agent 标记并打入冷宫，从而保证长期可用性。

这种“双引擎存储 + 混合检索 + LLM 蓝图拼装”的机制，就是当前工业级 Agent 解决“记忆膨胀”的核心解法。
