Agent 内部构建一条**从“耗能思考”到“直觉反应”的进化路径**——让 Agent 能像人一样，积累经验，形成“肌肉记忆”，并在未来遇到相似任务时，有意识地“抄自己作业”。

核心方案：“Dify 底座 + LangGraph”的架构，核心在于：**沉淀物的形态和被调用的方式**，即 **Agent 自主检索并决定复用“经验”**。
* Dify 负责：团队统一门户、知识库管理与 RAG、普通工作流（非研发可编排）、工具注册/权限/复用、对话日志/分析/成本管控 
* LangGraph 负责：复杂的、有明确状态机的长流程，需要持久化状态并支持人工干预的流程，对可靠性要求极高的执行流
* 协作文案：“在 Dify 里，LangGraph 服务被封装成一个‘自定义工具’，Dify 工作流或 Agent 在需要时调用它”

### 一、Agent 的“双系统”决策模型

我们将 Agent 的决策中枢设计为两个系统：

- **系统一（快思考/直觉）**：一个不断增长的**经验库**。存储的是“问题特征 → 已验证的最佳工作流（Workflow）或工具调用序列（Tool Call Sequence）”的映射。执行成本极低。
- **系统二（慢思考/推理）**：传统的 Agent 循环（思考-观察-行动）。遇到新任务时进行完整规划，成本高、但能解决未知问题。

**工作流程变为：**
1.  用户向 Agent 提出一个任务。
2.  **【新增】经验匹配节点**：Agent 首先将任务向量化，去经验库中检索语义上最相似的历史成功案例。
3.  **Agent 自主决策**：根据检索结果的相似度分数和上下文，判断是**直接复用**经验，还是**启动完全推理**。
    -   **高相似度（如 >0.95）**：直接执行经验中的工作流，填入参数，返回结果。Token 消耗趋近于零。
    -   **中等相似度（如 0.7-0.95）**：将经验作为“强烈建议”的参考上下文，放入提示词，让 Agent 进行微调。节省大量规划 Token。
    -   **低相似度（如 <0.7）**：视为新任务，启动常规的 Agent 完整推理循环。
4.  **【新增】经验沉淀回路**：当一个复杂任务通过系统二成功解决后，系统可以将此次的“思考路径+工具调用序列”作为一条新的经验，自动或半自动地存入经验库，供未来使用。

这个逻辑下，用户完全无感，他们始终面对同一个通用 Agent。Agent 自己会变得越来越快，越来越省 Token。这正是你想要的“运行后期成本越来越低”。

### 二、在 Dify 中构建“自进化 Agent”

可以在 Dify 平台内实现上述逻辑，不需要引入额外复杂组件。
LangGraph 继续负责它最擅长的“长流程状态机”，但这个进化逻辑是发生在 Dify 的 Agent 编排层面的。

#### 核心组件构建

1.  **经验库**
    -   **形态**：一个独立的 Dify 知识库，开启向量检索。或者一个专门的向量数据库（如 Milvus / Qdrant），通过 API 接入。
    -   **存储内容**：每条经验是一个文档。
        -   **索引内容（用于检索）**：用户任务的完整描述、上下文。比如：“我需要处理一个设备报修，用户描述是电脑蓝屏，代码xxx”。
        -   **经验内容（存储在工作流变量中或文档元数据里）**：一个结构化的“可执行流程模板”，如一个 JSON，描述了具体使用哪个 Dify 工作流及其参数映射，或是一系列工具调用的顺序和参数提取逻辑。

2.  **核心工作流：带“经验回路”的智能 Agent**
    -   在 Dify 中创建一个 **“工作流”类型应用**，这是中枢。
    -   **节点设计**：
        -   **开始节点**：接收用户输入。
        -   **经验检索节点（知识库检索）**：将用户输入去经验库中检索，返回最相似的经验片段及其相似度分数。
        -   **条件判断节点（LLM 决策）**：让 LLM 根据“用户任务、检索到的经验内容、相似度分数”三个信息，做一个单一决策：是“直接复用经验”、“参考经验推理”，还是“全新推理”。输出一个枚举值。
        -   **三个执行分支**：
            -   **复用分支**：解析经验文档中的“可执行流程模板”，动态调用一个“子流程执行器”节点（详见下文），填入参数，快速返回。
            -   **参考分支**：将经验内容注入 LLM 节点的提示词，然后进入普通的 Agent 循环，但引导其优先参考经验。
            -   **新建分支**：纯粹的 Agent 循环，无任何历史包袱。
        -   **经验沉淀分支（并行或异步）**：当“参考分支”或“新建分支”成功完成时，触发一个“经验总结节点”。这个节点调用 LLM 或代码，将本次成功的完整上下文（用户问题、调用的工具、步骤、关键参数）总结为一条符合经验库格式的文档，**自动存入经验库**。可以加上人工审核节点，确保质量。

3.  **子流程执行器**
    -   这是复用经验时的执行引擎。它接收一个流程定义（如：`调用“查库存”工具 → 调用“创工单”工具 → 调用“发邮件”工具`），并严格按顺序执行，填入从当前对话中提取的参数。
    -   在 Dify 中，可以用 **“循环+条件+代码执行”** 节点组合实现，或者通过调用一个外部的通用工作流执行微服务来完成。LangGraph 恰好可以完美承担这个“子流程执行器”的角色，因为它天然就擅长执行带状态的、确定性的工具调用序列。

#### LangGraph 的新定位：高可靠的“经验执行器”

在这个方案里，LangGraph 的职责变得更清晰和聚焦

-   **它不再是“需要人选择的复杂应用”，而是被 Agent 自动调用的“经验脚本引擎”**。
-   每当 Agent 决定复用某条经验时，它会调用一个 Dify 工具，该工具内部将经验中的流程定义和参数传递给 LangGraph 服务，由它严格、可靠地执行。
-   LangGraph 的状态持久化和错误处理能力，保证了这些被复用的“最佳实践”能以生产级标准可靠运行，即使它们包含长等待或复杂分支。

LangGraph 状态持久化（Checkpointer）的本质价值

* LangGraph 原生支持使用数据库（Postgres/SQLite）存储执行状态
* 这保证了服务重启、崩溃后，流程能从中断处精确恢复
* 这是 LangGraph 相比普通工作流（如 Dify 原生工作流）在“长流程/跨天流程”场景下的本质优势

### 三、阶段性开展的操作步骤

#### 阶段一：建立基础 Agent 和可复用的经验回路

1. **部署 Dify，完成基础建设**：按之前的方案，搭建好平台、封装好内部 Skills、让团队用上普通 Agent。
    1. Dify 私有化部署的关键环境变量（如 SECRET_KEY、DB_USERNAME、DB_PASSWORD、REDIS_HOST 等）
    2. LangGraph 服务的数据库连接配置（用于 Checkpointer）
    3. 两个服务之间的网络互通要求（同 VPC 或内网可达）
    4. 建议使用容器平台（如 Kubernetes 或 Docker Compose）统一管理
2. **创建“经验库”知识库**：在 Dify 中创建一个专用知识库，命名为 `Agent_Experience_Library`，设置好向量检索。
3. **开发“经验总结与存储”工具**：
    -   写一个 Dify 代码工具或 API 工具，接收参数：用户问题、成功的工具调用历史（JSON格式）。
    -   工具内部调用 LLM，将这些信息转化为经验文档，格式示例：`问题摘要：...；解决方案工作流：[步骤1: 调用工具A, 参数映射: {...}, 步骤2: ...]`。
    -   调用 Dify 知识库 API，将此文档存入 `Agent_Experience_Library`。
4.  **在 Agent 工作流中加入总结节点**：修改现有的 Agent 工作流，在成功结束前，并行调用上一步的“经验总结与存储”工具。**初期可开启人工审核**，确保经验质量。

#### 阶段二：实现“经验检索与决策”智能回路

1.  **在 Agent 工作流开头，插入经验检索节点**。
2.  **设计决策提示词**：编写一段精确的 `SYSTEM_PROMPT` 给决策 LLM。
    > “你是一个任务路由器。现在有一个用户任务：`{{user_query}}`。我们在经验库中检索到了以下可能相关的历史经验：`{{experience_text}}`，其语义相似度为 `{{similarity_score}}`。
    > 请判断：
    > - 如果经验高度吻合，仅需替换几个参数，回复 `REUSE`。
    > - 如果经验有参考价值但不能完全照搬，回复 `REFERENCE`。
    > - 如果经验完全不适用或相似度低，回复 `NEW`。”
3.  **构建三个分支**：
    -   `REUSE` 分支：指向 **“通用经验执行器”**（现阶段可以先用一个简单的代码执行链，或封装好的 LangGraph 工具）。
    -   `REFERENCE` 分支：将经验注入到 Agent 的上下文窗口中。
    -   `NEW` 分支：保持原有 Agent 逻辑。
4.  **开发“通用经验执行器”**：
    -   最简单版：在 Dify 中用代码节点解析经验的 JSON 流程描述，在一个循环中依次调用工具节点。但循环调用工具有限制。
    -   **推荐版**：将经验流程描述发送给一个独立的 LangGraph 微服务。这个服务只有一个通用状态图，能动态加载并执行一串工具调用序列。这样既能处理长流程，又非常可靠。
    -   将该服务封装为 Dify 的“自定义工具”，如 `Execute_Experience_Flow`。

#### 阶段三：持续进化与调优

-   **自动冷启动**：初期经验库为空，Agent 走 `NEW` 分支。随着使用，经验自动积累。你可以导出高质量的 Agent 对话日志，批量生成第一批“种子经验”，快速启动。
-   **经验治理**：
    -   **去重与合并**：定期运行脚本，分析经验库中相似的文档，合并为更通用的经验。
    -   **失效监控**：如果某条经验被复用但执行失败（工具报错、逻辑错误），自动标记或降权该经验。
    -   **人工工坊**：每月组织研发和业务骨干，将高频“参考”经验精炼为更健壮的“复用”经验。
    -   在 Dify 里设立“团队最佳实践”文件夹，将沉淀下来的通用应用发布为模板
    -   利用 Dify 的“日志与标注”功能，分析哪些固化流程被高频使用、哪些步骤经常出错
    -   定期（如每月）由研发和业务骨干一起，优化 LangGraph 状态机或 Dify 工作流

### 复用的本质：用“确定性执行”取代“推理循环”
理解“低Token复用链路”的实现，关键是转变一个观念：**Agent是“思考者”，而复用链路中的执行器是“执行者”**。Agent的每一步行动都需要LLM思考、规划，而执行器只是机械地按照既定剧本执行，只在必要时才让LLM做一点简单的参数提取工作。

对比一下两种模式：

**普通Agent模式（慢思考）**
> 每一轮循环：LLM观察结果 → 思考下一步 → 生成工具调用。
> 完成一个3步的任务，可能需要调用LLM 3-5次，每次都要输出完整的推理链和函数调用，Token消耗巨大。

**复用模式（快执行）**
> 经验库中已经存好了成功的步骤序列。
> 执行器拿到这个序列后，**完全不问LLM“下一步该做什么”**，而是像一个脚本解释器，按顺序执行工具，并用模板引擎填充参数。
> 整个过程可能只调用0-1次LLM（仅用于从用户自然语言中提取结构化参数），Token消耗断崖式下降。

**所以，保证低Token的关键设计是：**
1.  **去除决策LLM**：执行器本身不含任何“我该调用哪个工具”的推理逻辑，这个逻辑已在经验中被固化了。
2.  **参数传递模板化**：绝大多数参数通过`{{}}`占位符直接从上下文（用户输入、前面步骤的输出）中取，无需LLM理解。
3.  **只在“从非结构到结构化”的边界上，引入一次极轻量的LLM调用**。

### 实现机制的核心：动态可加载的经验模板 + 通用执行状态图

我们定义一个标准的**经验模板**，它描述了一次成功任务中的**全部必要信息**。这个模板存储在经验库中（向量数据库或Dify知识库）。

#### 经验模板的结构示例（JSON格式）

```json
{
  "id": "exp_it_ticket_001",
  "description": "处理IT设备报修：知识库查不到时就创建工单并通知",
  "required_inputs": ["user_query", "user_id"],
  "steps": [
    {
      "step_id": "1",
      "tool_name": "it_knowledge_search",
      "params": {
        "query": "{{user_query}}"
      },
      "save_output_as": "kb_result"
    },
    {
      "step_id": "2",
      "tool_name": "create_jira_ticket",
      "params": {
        "title": "IT报修：{{kb_result.top_issue_title}}",
        "description": "用户问题：{{user_query}}\n知识库建议：{{kb_result.summary}}",
        "reporter": "{{user_id}}"
      },
      "save_output_as": "ticket"
    },
    {
      "step_id": "3",
      "tool_name": "send_email",
      "params": {
        "to": "it-team@company.com",
        "subject": "新工单 #{{ticket.key}} 已创建",
        "body": "请尽快处理：{{ticket.url}}"
      }
    }
  ]
}
```

#### 通用经验执行器（LangGraph微服务）

这个微服务内部只有一个**元状态机**，它的工作是：

1.  **接收参数**：`experience_id`（或直接传入模板JSON）和 `initial_inputs`（如`user_query`, `user_id`）。
2.  **加载模板**：从数据库或内存缓存中读取经验模板。
3.  **动态构建一个状态图**：为模板中的每一个step创建一个图节点，并串联成一条线。这个图没有分支，没有LLM节点，是纯粹的执行流。
4.  **执行上下文**：维护一个全局的 `context` 字典，初始包含 `initial_inputs`。
5.  **每个节点的执行逻辑**：
    -   用**模板引擎**（如 Jinja2）渲染当前步骤的 `params` 对象。
    -   渲染的数据源就是 `context`，比如 `{{user_query}}` 直接从上下文取，`{{kb_result.summary}}` 是从上一步保存到上下文的结果中取。
    -   调用对应的工具（通过HTTP调用工具API，或直接调用Python函数）。
    -   将工具返回的结果，以 `step_id` 为 key 存入 `context`，供后续步骤使用。
6.  **状态持久化**：LangGraph 的 Checkpointer 会自动把每一步的 `context` 和当前节点位置持久化到数据库。如果执行中断，可以恢复，这是 LangGraph 的天然优势。
7.  **返回最终结果**：所有步骤执行完毕后，返回最后的 `context` 或某个指定的输出。

**关键点：在整个执行流程中，没有一个节点是调用LLM来决策的。所有的“智能”已经被编码在经验模板的步骤顺序和参数映射规则里了。**

### 关键实现：如何处理“从自然语言提取参数”

上面的例子中，`user_id` 可能是从会话上下文直接获取的元数据，所以可以直给。但如果参数藏在了用户非结构化的自然语言里，比如：

> 用户说：“帮我明天下午请个假，带娃打疫苗。”

复用经验需要调用 `hr_apply_leave` 工具，其参数 `start_time` 和 `end_time` 无法直接从上下文取，必须从这句话里提取。

**为了依然保持低Token，我们采用“一次性参数提取器”设计：**

在经验模板的步骤中，允许定义一种特殊的参数提取方式，而不是让LLM参与执行逻辑。

```json
{
  "step_id": "1",
  "tool_name": "hr_apply_leave",
  "params": {
    "start_time": "{{extracted.leave_start}}",
    "end_time": "{{extracted.leave_end}}",
    "reason": "{{extracted.reason}}"
  },
  "param_extraction": {
    "source": "{{user_query}}",
    "instruction": "用户想请假，提取：leave_start(ISO datetime), leave_end(ISO datetime), reason。现在时间是2026-07-06。返回JSON。",
    "model": "gpt-3.5-turbo",  // 可指定极便宜的模型
    "save_extraction_as": "extracted"
  },
  "save_output_as": "leave_result"
}
```

**执行这个节点时，逻辑是：**
1. 检查是否有 `param_extraction` 定义。
2. 如果有，**仅在这一步，一次性调用指定的廉价模型**（如 GPT-3.5，甚至一个微调过的轻量模型），传入 `source` 和 `instruction`，获取结构化的JSON提取结果，存入上下文的 `extracted` 字段。
3. 然后用 `extracted` 去渲染 `params` 模板，调用真正的 `hr_apply_leave` 工具。

**整个复用流程的Token消耗：** 仅一次极短的结构化提取调用，约100-200 Token。对比原始Agent可能要耗费几千Token进行多轮推理，消耗降低了超过90%。

如果你希望更进一步，对于高频且固定的提取场景（如请假、报销），可以直接接入内部已训练好的NER模型或正则规则，实现 **0 Token消耗**。

### LangGraph通用执行器 与 Dify 集成

1. **开发 LangGraph 微服务**：包含通用经验执行器，启动一个API。
    1. 用 FastAPI 或 Flask 包裹 LangGraph 应用
    2. 核心 API 1：POST /invoke —— 接收 Dify 传入的参数，启动或继续一个状态机，返回最终结果或“需要外部输入”的提示
    3. 核心 API 2：POST /resume（可选）—— 当流程在 Dify 中收到了人工输入后，调用此接口让状态机继续
2. **在 Dify 中注册为“自定义工具”**：
    -   工具名：`Execute_Workflow_Experience`
    -   输入参数：`experience_id` (string), `user_query` (string), `user_id` (string, 或其他从会话中可得的元数据)
    -   输出：执行器返回的最终结果JSON。
3.  **在 Dify 的“带经验回路的工作流”中配置**：
    -   当决策 LLM 输出 `REUSE` 时，工作流走向一个“工具调用”节点，调用 `Execute_Workflow_Experience`，并将检索到的经验ID、当前用户输入等传入。
    -   该工具执行期间，Dify 工作流处于等待状态，不消耗额外 LLM Token。
    -   执行完毕，工具返回的结果直接作为工作流的最终输出返回给用户。

这样，整个 REUSE 链路的 LLM 消耗就仅仅发生在：**① 决策 LLM 的一次简单判断（极其微量）** + **② 执行器内部可选的一次性参数提取**。

### 一个例子，感受Token消耗的剧降

#### 场景：用户报销“去上海出差的高铁票，金额500元”

**A. 传统Agent模式（慢思考）**
